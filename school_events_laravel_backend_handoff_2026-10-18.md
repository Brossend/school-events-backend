## 3. Выбранный стек и роли агентов

### Зафиксировано

- **Backend: Laravel (PHP)**, а не Go. Решение принято из-за скорости разработки, богатой экосистемы, знакомого пользователю PHP и отсутствия значимой CPU-нагрузки в CRUD/LLM-оркестрации.
- **База: PostgreSQL.**
- **Redis и Laravel Queues** для фоновой генерации, проверки и экспорта.
- Контейнерное локальное окружение **Docker Compose**.
- Backend представляет стабильное **JSON REST API** для frontend. UI планируется на Vue 3 + TypeScript, реализация frontend позднее по Figma MCP.
- Проект — **модульный монолит**, не нужно изобретать микросервисы под учебный MVP.

### Предлагается (НЕ утверждено заказчиком и должно быть согласовано по ходу)

- Поддерживаемая стабильная версия Laravel и совместимый PHP; выбрать после проверки окружения, не фиксировать устаревшие версии только из прошлого переписывания.
- Laravel Sanctum для SPA/API; выбрать cookie-based или token-based схему по будущему размещению frontend.
- Ролевая/ресурсная модель: teacher, school_admin, catalog_curator/editor и system_admin; минимизировать до реальных сценариев. Все школьные проекты изолированы по `school_id`, Laravel Policies обязательно.
- S3-compatible object storage **или** локальное файловое хранилище в MVP с заменяемым адаптером, без утечки приватных файлов в публичный URL.
- Feature/Integration tests PHPUnit/Pest; API-schema и service tests; отдельные фикстуры/mock для LLM. Не начинать со сложной DDD-схемы.

### Организация работы

ChatGPT в новом чате — **архитектор, постановщик задач и независимый ревьюер**. Codex (предпочтительно) — основной исполнитель; Gemini можно использовать для независимого ревью, но не параллельно менять те же файлы. Каждую фазу закрывать после рабочих миграций, тестов, evidence и отчёта по изменённым файлам. Не скрывать тестовые падения и не маркировать фазу CLOSED при известных P0 дефектах.

## 4. Исходные требования (из шестистраничного ТЗ)

Продукт соединяет **федеральные события, региональные события, национально-культурные праздники, собственные школьные события**. Педагог выбирает событие и контекст, ИИ выдаёт адаптированный проект и материалы. Культурный каталог обязан исследовать конкретную культуру по источникам, а не выдумывать обряды и стереотипы.

**Календарь:** событие, тип, дата, регион, источники, описание, педагогически релевантный контекст. Параметры для проектирования: возраст, формат, продолжительность, участие семьи. Отличать ежегодные даты от **даты проведения отдельного мероприятия**; нельзя переносить дату областного фестиваля прошлого года на следующий без источника.

**Конструктор:** собирает доступный пользователю предметный контекст: событие (из календаря или своё), возраст/класс/число участников, регион, масштаб (классное / общешкольное / семейное), конкретный формат (классный час / квест / викторина / мастер-класс и т. п.), длительность, условия проведения, состав участников, родители/гости, доступные ресурсы, ограничения и ценностная цель.

**Шесть ценностных направлений из ТЗ — не теги:**

1. Семья → семейное исследование.
2. Взаимопомощь → командная задача.
3. Историческая память → работа с источниками.
4. Труд и созидание → совместный продукт.
5. Культурное многообразие → сравнительное изучение культур.
6. Гражданственность → решение реальной общественной задачи.

**ИИ-сценарист** выдаёт **полный пакет**: концепцию и цель, воспитательные задачи, ожидаемые результаты, подробный сценарий с временными интервалами/переходами/репликами и подсказками педагогу, роли участников, интерактивные задания, материалы и оформление для показа/печати (структуру или готовые презентационные материалы/карточки), реквизит, чек-лист подготовки и методические инструкции. В демонстрационных макетах: классное мероприятие 45 минут (5+7+15+12+6), семейное 60 минут (5+10+20+15+10), общешкольное 90 минут (10+15+30+20+15). Числа только демопримеры, реальные зависят от ввода.

**Модерация до выдачи пользователю — ОБЯЗАТЕЛЬНО:**

- P0: этнические/расовые стереотипы, дискриминационные формулировки; недостоверные и выдуманные культурные факты/традиции. Их нельзя выдавать как готовый сценарий: блокировка, корректировка/перегенерация и повторная проверка.
- P1: соответствие возрасту, безопасный доступный формат; базовая методическая целостность (цель, задачи, сумма таймингов, роли, переходы, инструкции).
- Проверка ИИ **не равна абсолютной гарантии** отсутствия ошибок. Фактические утверждения требуют evidence; без верифицируемых источников исключать или маркировать для ручной проверки, а не произвольно отмечать «подтверждено».
- После автоматической проверки педагог просматривает/редактирует сценарий и **отдельно вручную подтверждает**, что он готов для проведения. Нельзя автоматически ставить ручной sign-off по ответу LLM.

**Собственные школьные традиции:** школа сохраняет собственный ежегодный повод, концепцию и библиотеку сценариев; на новый учебный год создаёт **новую версию** с актуализированными параметрами, не перезаписывая архивную. Подтверждения прошлогодних источников не должны автоматически наследоваться для новых событий.

**Экспорт и материалы:** полноценный PDF/DOCX, включая сценарий, роли, тайминг, раздатку и рекомендации, плюс предусмотренные макеты презентаций/карточек. В Figma нарисованы четыре листа A4 и пять слайдов 16:9, но файлы пока не генерируются.

## 5. Приёмка и пилот

По ТЗ тестирование с **20 педагогами**, реальные результаты пока **отсутствуют**. Гипотезы и целевые пороги:

| Метрика | Критерий | Метод |
|---|---|---|
| Скорость | медиана сокращения времени подготовки **≥ 50%** | сопоставить базовую и ИИ-подготовку для каждого педагога, потом медиана индивидуальных долей |
| Персонализация | **≥ 70%** выбрали персонализированный сценарий | универсальный vs адаптированный при одинаковой задаче |
| Объём ручной доработки | **≥ 70%** педагогов оценивают доработки как **≤20%** | метод расчёта доли изменений зафиксировать до исследования |
| Культурный контекст | **≥ 60%** педагогов используют его | два варианта контента с контекстом/без него |
| Полезность версии с культурным контекстом | **≥ 4/5** | субъективная оценка педагогов |
| Критические культурные ошибки | **0** | отдельная экспертная проверка/протокол, не самооценка LLM |

Измерения хранятся без ФИО детей; идентификатор педагога можно делать анонимным кодом. Не подставлять демо-значения как реальные результаты, статус «нет данных» до получения ответов.

## 6. Данные (предлагаемая серверная модель, не готовая схема)

Главные сущности и связи для обсуждения перед миграциями:

- `users`, `schools`, `school_memberships`/school roles: изоляция школ и доступ сотрудников.
- `calendar_events`, `event_occurrences`, `event_sources`, при необходимости `cultural_claims`, `source_reviews`: тип, дата и её вид, регион, культурная информация, provenance, документ, статус редактора (`candidate/pending_review/approved/rejected`), кто и когда проверил.
- `school_traditions`, `tradition_versions`: собственная ежегодная концепция, учебный год, базовая версия, отдельная история без потери прежних редакций.
- `scenario_requests`: исходные параметры конструктора в виде валидированной структуры + snapshot контекста/версии каталога.
- `scenarios`, `scenario_revisions`, `scenario_stages`, `scenario_materials`: сгенерированный документ, текущая/архивные редакции, структурированные этапы и блоки для DOCX/PDF.
- `generation_runs`: провайдер/model ID, prompt/schema version, время, попытки, код ошибки, статус задачи, usage при доступности, аудируемая ссылка на запрос/ответ без секретов.
- `verification_runs`, `verification_findings`, `verification_evidence`: правила, severity P0/P1, source references, статус blocked/warnings/pass, исходная и исправленная версия, повторная проверка.
- `teacher_signoffs`: ручное подтверждение конкретной ревизии; после редактирования ревизии sign-off надо сбрасывать/потребовать переподтверждения.
- `export_jobs`, `artifacts`: PDF/DOCX/возможные печатные шаблоны, состояние `queued/running/ready/failed`, путь к реально созданному файлу, размер, срок ссылки/доступ.
- `pilot_participants` (псевдонимизированно), `pilot_responses`, `pilot_review_findings`: исходные ответы, валидность, наблюдения, экспертные ошибки и статистика.

Все названия таблиц **предложения**; агент должен оптимизировать нормализацию и ограничения PostgreSQL, сделать ERD и зафиксировать реальную миграционную схему перед кодом. Долгие LLM-запросы — jobs, не держать 120-секундный HTTP request.

## 7. Предлагаемые границы API (это ещё не финальный контракт)

- `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/me`; восстановление пароля с нейтральным ответом независимо от существования email.
- `GET /api/calendar-events?region=&from=&to=&type=&q=`, `GET /api/calendar-events/{id}`; управление модерацией только авторизованному куратору.
- `GET/POST /api/schools/{school}/traditions`, `GET/POST /api/traditions/{id}/versions`.
- `POST /api/scenario-requests` (валидация всех параметров), `POST /api/scenario-requests/{id}/generate` (асинхронная задача), `GET /api/generation-runs/{id}` (статус).
- `GET /api/scenarios/{id}`, `PATCH /api/scenarios/{id}` или отдельный endpoint ревизий; optimistic locking/version check против потери параллельных изменений.
- `GET /api/scenarios/{id}/verification-runs`, `POST /api/scenarios/{id}/verify` (автоматическая повторная проверка), `POST /api/scenarios/{id}/signoff` (ручной, только разрешённым педагогом и после устранения P0).
- `POST /api/scenarios/{id}/exports` с `format=pdf|docx`, `GET /api/export-jobs/{id}`, затем авторизованное получение готового файла.
- `POST /api/pilot-responses`, `GET /api/pilot-results` с правами доступа.

Рассмотреть API versioning `/api/v1/...`, единый envelope ошибок (`code`, `message`, `details`, `trace_id`) и статусы `422`, `403`, `404`, `409`, `429`, `503`; OpenAPI YAML в репозитории. Не придумывать конкретные слоты и таблицы раньше дизайн-контрактов.

## 10. Строгие правила

1. «Проверено ИИ» ≠ «педагог подтвердил»; вручную отмечается только человек и только конкретная ревизия.
2. Неподтверждённая дата/источник/культурный факт ≠ утверждённое событие; никогда не симулировать факт как источник.
3. Не передавать пользователю материал с P0 находками как безопасный готовый сценарий; при сомнениях не обещать абсолютной автоматической гарантии.
4. История учебных лет/версий не перезаписывается.
5. Экспорт `ready` означает, что байты файла существуют, доступны авторизованному пользователю и относятся к правильной версии.
6. `success` в пилоте означает фактические валидные ответы и определённую методику расчёта, а не моковый счётчик.
7. Design v1.0 зафиксирован; API проектируем по Figma и ТЗ. Существенные UX/схемные расхождения согласовываем отдельно.
8. Нельзя заявлять, что backend уже существует: он ещё не создан.
