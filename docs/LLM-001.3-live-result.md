## Валидация и repair

Оба варианта содержат реальные Scenario и ScenarioRevision. До отзыва evidence у A и B: `technical_checks=passed`, `status=requires_review`, ошибок Quality Gate нет. Оригинальная JSON Schema, Semantic Validation, соответствие запросу и проверка готовности материалов пройдены штатным pipeline. Локальное повторное применение схемы, Semantic Validation и material validator к сохранённым live payload также прошло. Повторный RequestedScenarioValidator после отзыва закономерно отклоняет B с `LLM_PROVENANCE_CHANGED`; это отдельная фаза, не ошибка генерации.

В обоих вариантах repair карточек был **`materials.printable_cards.card_4.back_text`**: добавлен отсутствующий закрытый числовой ключ `3 комплекта, расход 15/9, остаток 3/3`. Проверка сохранённых original/patch/final подтверждает:

- Все остальные поля пяти карточек, включая front_text и соседние back_text, побайтно по значениям JSON сохранены; handouts также сохранены.
- Все незатронутые верхнеуровневые разделы сохранены; перечни — в `acceptance-checks.json`. Адресные слайды B изменялись отдельным штатным repair.
- Длины front_text A: **285, 323, 324, 276, 282**; B: **208, 217, 222, 175, 126**. Все >=120; back_text >=40. Укороченных 97-символьных результатов нет.
- Числовой ответ находится на обороте; на лицевых сторонах сохранены распределённые исходные данные и вопросы без готового результата. Проверки математики и порядка выдачи материалов прошли; ключ корректен: 3×5=15, 3×3=9, остаток 3/3; дополнительный лист даёт остаток бумаги 2 и нарушает минимум 3.
- В live-попытке не потребовался repair самого front_text. Защита от прежнего 97-символьного patch подтверждается focused offline regression, а live подтверждает адресное изменение back_text без повреждения front_text.

## Cultural coverage и отзыв evidence

Собственное тестовое evidence программно получило `verified_authentic` через штатные API review/evidence. Оно связывает CulturalClaim о дате 4 ноября с цитатой из нормативного источника; синтетический reviewer проверяет программный контракт, а не даёт экспертную историческую аттестацию.

До отзыва: B доступен, три supported assertions, `whole_document_verified=false`, coverage `requires_review`. Осталась одна review-находка `UNSUPPORTED_CULTURAL_TEXT`; отсутствие ошибок не объявлено полной исторической проверкой. A также `requires_review`, без подтверждения всего документа.

После DELETE собственного evidence перечитаны comparison и оба payload/quality review: B недоступен, supported assertions=0, Quality Gate B=`blocked`, technical_checks=`failed`; A остаётся допустимым. Сохранённые исходные revisions не переписывались.

1. Попытка выбрать B **до фиксации какого-либо выбора**: HTTP **409**, `CONFLICT`, «Вариант B недоступен для выбора, так как в системе отсутствуют верифицированные первоисточники.»
2. Выбор A: HTTP **200**, `selected_variant=A`.
3. Последующая попытка выбрать B: HTTP **409**, `CONFLICT`, «Выбор для данной сессии сравнения уже зафиксирован и не подлежит повторному изменению.»

Таким образом, отказ provenance и отказ immutable selection получены отдельно и имеют разные реальные серверные причины.
